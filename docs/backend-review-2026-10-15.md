**R01 · P1 · 未认证访问者可使用服务器预配置 Cloudflare Token 改写 DNS**

位置：`internal/application/setup.go:143`、`:173`；`internal/adapter/httpapi/setup.go:121`、`:242`；`internal/application/setup_dns.go:79`。

触发条件：内置正式模式尚未初始化，配置了 `CLOUDFLARE_API_TOKEN`，Setup 入口可访问。自动初始化因记录不匹配、DoH 或预检问题暂停时同样满足条件。配置 `ADMIN_PASSWORD` 不能阻止该路径。

`GET /api/v1/setup/status` 公开返回 `setup_id`。随后 DNS preview/confirm 仅检查请求 Origin 与 Host 相等，`configuredToken` 只验证公开的 ID，然后取出服务器 Token。DNS 确认没有验证管理员密码，也没有把操作绑定到部署者授权的域名和目标 IP。HTTP 客户端可以自行设置匹配的 Origin；这不是身份认证。

隔离复现采用真实 Setup handler 与 application Service，DNS 写入使用替身：匿名 GET 获取 ID；两个 POST 使用 `use_configured_token:true` 完成预览和确认。全程没有发送密码、Cookie 或 Token，却进入 DNS `Apply`。默认域名为 `intended.example.com`，实际请求操作 `unrelated.example.org`，目标 IP 由调用者指定。

影响是代理使用 Token 权限，而非泄露 Token 明文。调用者可修改该 Token 权限范围内、满足现有记录冲突规则的通配符记录，造成流量重定向或服务中断。不能把这个问题扩大为任意 DNS 类型和任意记录写入。

修复建议：交互使用服务器预配置凭据前，验证部署者持有的初始化授权证明，例如用预配置密码建立短期 Setup 会话，或使用一次性部署秘密。`setup_id` 继续用于状态版本绑定，不能作为授权凭据。只固定域名仍不够，因为调用者仍可能把该域名改向未经授权的 IP。保留服务端自动流程的无警告、只读复用路径。

回归要求：匿名、错误密码、仅公开 ID 均不能触发预配置凭据的 DNS 读写或 secret 写入；覆盖合法会话、过期、CSRF、非默认域名/IP，以及自动流程暂停后人工接续。

**R02 · P1 · 内置模式漂移恢复被证书前置检查阻断**

位置：`internal/application/deploy.go:19`、`:27`、`:135`、`:177`、`:248`。

`publicCertificateReady` 不仅检查证书，还要求 `runtimeMatchesSnapshot`。`Validate` 和 `Begin` 都先调用这个门禁。因此，只要内置 Caddy 的实际配置与启动快照不同，即使证书探测结果可信，校验仍返回 `public_certificate_pending`，无法取得有效 validation ID，也无法到达后面的 `ConfirmDrift` 分支。

隔离测试中，Preview 正确返回 `drift:true`，证书替身始终可信，但 Validate 返回“请先启用并等待公网可信证书就绪”。这不是证书故障，而是两个独立条件被混用。

影响：文档描述的“核对漂移 → 重新校验 → 明确确认覆盖”在内置模式不可完成，且错误提示把用户引向证书操作。外部模式提前返回 true，不受同一门禁影响。

修复建议：分离公网证书检查与运行配置一致性检查。漂移应由实际运行指纹、校验绑定、明确确认和加载前复核控制；未决发布仍须阻断。不能简单删除漂移检查或默默覆盖。

回归要求：内置模式可信证书 + 实际漂移时能够预览和校验；无确认拒绝 Begin；有确认且运行指纹未再次变化时允许；第二次漂移必须再次刷新。

**R03 · P1 · 临时证书清理缺少可恢复的持久化操作记录**

位置：`internal/application/certificates.go:90`、`:107`、`:126`、`:149`、`:157`；`internal/application/deploy.go:333`。

`CertificateState` 在读状态时触发清理：读取快照、生成移除临时证书的候选、加载 Caddy、读回核对、写启动快照。这个配置写入不使用普通发布意图，也没有独立的持久化清理意图。

已复现：Caddy 加载成功，随后快照写入失败。此时运行配置已经移除临时证书，快照仍是旧配置。存储恢复后再次读取证书状态，因为运行与快照不一致，清理分支不再执行；`Recover` 只检查普通 pending deployment，也无法修复。状态一直为 pending，并触发 R02 的发布阻断。

修复建议：把证书清理作为有持久化候选、旧/新指纹和阶段记录的内部配置变更；共用可靠的配置写入与恢复逻辑。清理请求可以由后台状态检查触发，但在任何 Load 之前应有可恢复意图。成功加载后即使写盘失败、请求取消或进程退出，重启也应能够核对并完成快照更新。

回归要求：分别在 Load 前、Load 后、读回失败、原子 rename 前后、状态保存失败处注入故障；恢复后运行指纹、快照和证书状态一致，不丢失业务配置，不改写历史发布 JSON。

**R04 · P1 · `manager run` 绕过实例锁执行恢复写入**

位置：`cmd/manager/main.go:61`、`:82`；`cmd/manager/container.go:40`、`:55`、`:128`、`:141`。

`run` 在进入实例锁逻辑之前直接调用 `runContainer`。监督流程打开可写数据库并执行 `reconcileCertificateActivation`，之后才启动 Caddy 与 `serve`；只有 `serve` 子进程取得锁。

当另一个 Manager 或密码维护进程已持锁时，第二个 `run` 仍可读写同一实例。明确场景是证书激活处于 applying，旧启动快照仍等于 BeforeHash：重复启动会把激活改成 failed，清空恢复哈希并写审计。此时已有 Caddy 并没有从旧快照重启，“启动快照现在是权威状态”的前提并不成立。后续子进程因锁冲突退出也不能撤销先前写入。

修复建议：在可写数据库打开、恢复核对和任何子进程启动之前取得实例锁，由监督进程持有整个生命周期；为 `serve` 明确设计锁继承或监督模式锁所有权，避免父子重复加锁。维护命令使用相同锁。

回归要求：预持锁并准备 applying 证书状态和旧快照，执行 run 必须立即拒绝，数据库、审计、证书文件不变且不启动 Caddy；覆盖 run/run、run/serve、run/reset-password 竞争。

**R05 · P1 · 默认部署依赖 README 没有创建的外部网络**

位置：`compose.yaml:32`；`README.md:16`；`compose.validation.yaml`。

默认网络声明为 `external:true`，名称固定为 `caddy-admin`；快速部署说明只有下载 Compose 和 `docker compose up -d`。干净 Docker 环境没有该网络时，Compose 不会自动创建它，启动失败。验证覆盖文件没有覆盖默认网络，源码验证也依赖并共享这个网络。

修复建议：默认由 Compose 创建按项目名隔离的网络；需要接入已有服务网络的场景用显式覆盖文件。同步快速部署与运维示例。

回归要求：无预置网络时按 README 启动成功；正式实例和源码验证使用不同项目名时网络隔离。`docker compose config --quiet` 只验证配置语法，不能发现外部网络不存在，本轮未进行干净 Docker 启动实测。

**R06 · P2 · 已接受发布的幂等查询依赖瞬时证书与运行状态**

位置：`internal/application/deploy.go:174`—`:190`。

`Begin` 在查找已有幂等记录之前执行 `requirePublicCertificate`。内置模式中，首次请求已经受理，客户端丢失响应后重发完全相同的幂等请求；如果此时 Caddy 暂不可达、证书探测失败或运行/快照暂时不一致，服务返回证书错误，而不是原部署结果。

已有部署不会因此被重复创建，但幂等重试不能可靠地帮助客户端找回已受理结果，尤其在故障时最需要这个能力。现有测试的正常重复提交没有覆盖此条件。

修复建议：完成请求基本合法性校验后，优先查找幂等键并核对 request hash；完全相同的已有请求直接返回持久化部署。仅对新发布执行当前策略和证书前置检查。保持键冲突拒绝和 HTTP 认证。

回归要求：首次接受后分别模拟 Caddy 断联、证书失败、校验过期及快照不一致，同键同请求仍返回原 ID；同键不同请求始终冲突。

**R07 · P2 · 上游 DNS 故障阻止禁用服务**

位置：`internal/application/services.go:50`；`internal/domain/policy.go:137`、`:188`；`internal/application/deploy.go:92`、`:224`。

保存非删除操作、预览以及发布前都对所有服务执行 `NormalizeService`。该函数无论 Enabled 状态都重新解析上游、检查当前地址并生成 Dial。

已上线服务的上游名称解析失败时，管理员将其改为禁用仍会失败；已经禁用的条目也可能因 DNS 故障阻止其他服务发布。删除该条目可以绕过，但用户失去保留配置的正常停用路径。`docs/api.md` 要求禁用服务保留合法配置，并不等于必须实时可解析。

修复建议：区分静态结构校验与启用路由所需的 DNS/目标校验。停用条目仍必须满足名称、域名、协议、端口等静态规则；因为不生成其代理路由，不应要求它实时可连接或可解析。再次启用时必须按当前安全策略完整解析、校验并绑定地址，不能复用旧 Dial 绕过检查。

回归要求：已发布服务解析失败后仍可保存停用并发布移除路由；草稿保留；再次启用被拒绝直至重新通过验证；禁用项不能污染启用项的路由生成。

**R08 · P2 · 正常保存的配置可能无法导出**

位置：`internal/application/configuration.go:45`、`:61`、`:84`；`internal/application/services.go:61`。

导出调用与导入共用的 `validateConfiguration`，超过 60 KiB 即返回错误。但逐个新增服务和保存备注没有同样的配置总量约束。

已通过真实临时 SQLite 复现：32 个各含 2000 字节合法备注的服务均能正常保存，调用 ExportConfiguration 却得到“配置文件不得超过 60 KiB”。不需要达到几百个服务。业务配置一旦增长，就可能失去项目承诺的导出能力。

修复建议：定义可往返的统一容量规则。优先允许导出完整合法数据，并相应设计有界的大文件导入接口；如果坚持总量上限，应在保存前明确拒绝超限，且为已经超限的数据保留导出方式。不能截断导出或要求用户先删数据。

回归要求：最大字段长度、连续添加服务、大型 settings、中文及转义字符都可以完整往返，或在保存前清晰拒绝；测试实际 HTTP 编码大小和导入外层封装开销。

**R09 · P2 · 概览忽略仅设置发生的未发布变更**

位置：`internal/application/status.go:21`。

`Overview.Unpublished` 只比较已发布服务与草稿服务，不比较 `draft.Settings` 和当前生效设置。修改 DNS 解析器、访问策略、观测开关或新增域名后，服务列表相同就返回 `unpublished:false`。

已复现：SaveSettings 把修订增至 1，Preview 返回 `settings_changed:true`，Overview 却返回未发布为 false。概览与发布页对同一状态给出矛盾反馈。

修复建议：统一“是否有待发布变更”的业务判定，包含服务模型和设置。普通服务变化、设置变化、首次初始化后的导入策略、回滚后保留的草稿都应遵循相同定义。

回归要求：分别只改访问策略、DNS、观测开关、域名及控制台交接字段，概览都提示未发布；成功发布后恢复一致。

**R10 · P2 · 跨时间桶的采样错误归属并误报完整覆盖**

位置：`internal/adapter/observability/store.go:91`—`:124`；`internal/application/observability.go:48`—`:62`。

采集 ticker 从进程启动时刻开始，并不对齐 UTC 的 15 秒边界。存储却将整个 from/to 区间的计数与覆盖秒数写入终点所在桶。

已复现：相对于某个桶边界，采样区间为 `[-8s,+7s]`，共 10 个请求。查询 `[0s,15s)` 返回全部 10 个请求、`coverage=1` 和 `complete=true`，实际该桶只覆盖 7 秒，且混入了前一个桶的数据。分钟、小时边界同样受影响，完整窗口参与告警判断时会放大误差。

修复建议：覆盖时间按区间与桶的交集累计；明确跨桶计数是近似分配还是保留原始采样区间，不得把缺失区间标为完整。对齐采集时刻只能减少误差，不能替代对延迟和抖动的处理。

回归要求：非零启动相位、跨分钟/小时、采集延迟、窗口边缘及 5 分钟告警查询，验证覆盖率不虚增、窗口外计数的处理有明确口径。

**R11 · P2 · 停采后数据保留期限失效**

位置：`internal/application/observability.go:147`—`:159`；`internal/adapter/observability/store.go:83`、`:134`—`:145`、`:278`。

过期清理只由指标 Write 或日志 AppendLogs 触发。关闭指标与日志后直接返回；长期配置漂移或源端不可达也会提前返回。访问日志、IP 网段和细粒度指标可以无限期保留在数据库中。查询接口禁止查询超期范围，不等于删除数据。

这与 `docs/operations.md:207`—`:213` 的“最多 7 天”“保留期限是时间上限”不符。清理本身按批执行，恢复后的积压清除也需要明确预算。

修复建议：独立定时维护任务负责过期清理，开关关闭和源端不可用时继续运行；启动后处理积压，并暴露清理失败/积压状态。涉及 SQLite 物理空间和删除痕迹的保证应与文档区分，不应把删除行等同于安全擦除。

回归要求：写入各层级数据后关闭开关、模拟持续断联、推进时间，直接查询数据库确认过期行被删除，未过期历史保留。

**R12 · P2 · 证书探测耗尽总预算后，告警状态更新失败并挤占 TCP 检查**

位置：`internal/application/observability.go:76`；`internal/application/alerts.go:117`—`:175`；`internal/adapter/caddy/probe.go:20`—`:24`。

每轮告警评估总预算 20 秒，先串行探测全部域名证书，每个域名最多 4 秒。固定 TLS 地址握手卡住时，几个域名即可耗尽预算，而产品明确支持最多 64 个观测域名。

证书结果收齐之后才持久化告警；此时 SaveAlert 使用的 context 可能已经取消，错误又被忽略，旧 active/resolved 状态无法更新为 unknown。TCP 循环因 `ctx.Err()!=nil` 完全跳过，未检查上游又被标为 seen，旧状态继续保留。这个情况可以每分钟重复。

修复建议：为证书和 TCP 检查分别分配预算，证书使用轮询或有界并发；超时结果使用独立短时持久化 context 写入 unknown/陈旧状态。保存失败不能静默吞掉。保留 Manager 视角的说明，不能将 TCP 成功称为应用健康。

回归要求：多个域名持续超时仍能更新未知状态，TCP 有合理预算或明确标记陈旧；模拟存储失败能显示采集/告警不可用，而非继续展示旧成功。

**R13 · P2 · 日志停采后状态仍为 ready**

位置：`internal/application/observability.go:123`—`:126`、`:156`—`:159`。

日志已正常采集后，遇到运行漂移、Caddy 不可达或未决发布，Collect 提前退出。`fail` 只修改指标 State 和 Message，不修改 LogsState。因此 `/observability` 可以持续返回 `state:unavailable`、`logs_state:ready`，实际上日志完全停采。

已通过应用层用例复现。当前日志状态缺少独立的最后成功时间，也无法让调用方判断 ready 已经过期。

修复建议：阻断全部采集的错误同步更新日志状态为暂停或不可用，保留已有日志与游标；指标单独失败时可以继续独立采集日志。增加日志最后成功采集时间及陈旧判定。

回归要求：日志 ready 后依次进入漂移、断联、pending、恢复；状态与实际采集一致，游标不倒退、不丢历史。

**R14 · P2 · 服务器 DNS 诊断接受无关名称的回答**

位置：`internal/adapter/caddy/setup_dns_lookup.go:55`—`:60`。

解析器检查了响应 ID 和 Question，却把 Answer 中全部 A/AAAA 都收集为地址，没有核对 owner name、CNAME 链、查询类型和类别。

隔离复现中，回环假 DNS 对控制台和随机子域问题只回答 `unrelated.example.org A 10.0.0.6`，没有相关 CNAME，DNSResults 仍对目标 `10.0.0.6` 返回 `verified:true`。

影响限定为服务器 DNS 诊断，尤其专家接口 `/api/v1/setup/dns/check`。普通向导的浏览器 DoH、自动初始化的服务端 DoH 有不同实现和名称过滤，不能据此声称绕过初始化或发布校验。

修复建议：只接受问题名称或有界、可追踪 CNAME 链上的对应类型/IN 类地址；无有效地址返回未生效。可复用已经在 DoH 解析中实现的验证规则，保持不同传输的结果一致。

回归要求：无关记录、正确与无关记录混合、跨类型回答、合法 CNAME 链、乱序链及循环链。

**V01 · 外部发布超时后延迟生效：状态机风险，需部署级验证**

位置：`internal/application/deploy.go:285`—`:294`、`:327`—`:328`；`internal/adapter/caddy/client.go:80`。

普通 Load 非确定性错误后，程序立即读取配置。如果这次仍是 BaseHash，就终结为 failed。后续 Recover 只处理 applying/uncertain，不会再检查这条 failed 记录。

端口替身测试已证明：Load 返回超时，第一次 Read 返回旧配置，发布被判 failed；随后模拟原 Load 延迟生效，Recover 不处理，运行配置与启动快照永久分离。

**证据限制**：这证明应用层状态机无法处理这种外部时序，不证明直连当前 Caddy 必然产生它。当前 Caddy 的配置加载和读取存在共享读写锁，加载已经进入其配置临界区时，读取通常不会立即拿到旧状态。外部代理在请求进入 Caddy 前排队、延迟转发或中间层返回超时，才是需要进一步验证的重点。因此本项单独列为风险，不计入上述 14 项确认问题。

建议：明确外部 Admin API 的请求排序与超时契约。对于无法证明请求未执行的超时，旧配置读数本身不应被视为最终失败证明；可持续保留 uncertain，直到有足够证据确认原操作终结。针对真实部署的代理/连接拓扑补充“超时后迟到 Load”集成用例，避免只测试“先成功加载再丢响应”。

**已核对的有效保护与不应误报的行为**

- 会话 Token 持久化使用哈希；Argon2id 密码哈希、Secure/HttpOnly/SameSite Cookie、管理 API 服务端认证和 CSRF 检查存在。密码更新事务撤销旧会话，发新会话时再次检查密码代际。
- 上游解析结果全部进行安全校验，再选定 IP 写入 Dial；HTTPS 上游生成 TLS server_name，没有通过关闭证书校验解决连接问题。证书概览虽然先抓取证书链，但随后显式做系统信任和域名验证，不能单凭 `InsecureSkipVerify:true` 就认定漏洞。
- 普通草稿变化不加载 Caddy。完整配置发布包含修订、策略、运行指纹和校验有效期约束，并有唯一 pending 数据库索引；失败快照保留 uncertain 的主流程已有测试。
- 在线回滚重新生成历史服务模型，保留未发布草稿，不直接重放任意历史运行配置；只允许成功版本。
- 外部 Caddy 保留 admin/storage，显示 JSON 时去掉这两部分；业务其余配置仍由本项目完整管理。没有把本地 Validate 等同于远端模块、Token 或存储可用。
- Cloudflare DNS 变更已有预览、上下文指纹、意图先持久化、读回和重试复用。R01 是调用者授权缺失，不意味着这些幂等保护不存在。
- SQLite 使用事务、WAL、FULL 同步、当前 schema 校验及权限设置；未知版本拒绝。没有发现足够证据把一般性“应该换数据库/重构架构”列为问题。

# DNSPod Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development to implement and review the independent tasks below.

**Goal:** Default to Cloudflare and fully support selecting DNSPod during Setup, from ENV or manual credentials, including DNS records, certificates, restart and recovery.

**Architecture:** Fixed provider selection (cloudflare/dnspod), one provider per instance. Reuse existing preview/confirm/reconcile workflows with provider-aware credentials and fingerprints. Persist selection; environment changes must not override initialized instances.

**Tech Stack:** Existing Go/Gin/SQLite and React/TypeScript; pinned caddy-dns/dnspod module.

**Spec:** User-approved design in conversation: Cloudflare default, DNSPod ID,Token, no AliDNS, full implementation.

## Global Constraints
- No real DNS writes or production credentials in tests.
- Setup remains three steps. Never echo credentials; JSON contains environment placeholders only.
- Preserve DNS conflict checks, confirmation, uncertain-write reconciliation, authentication and deployment recovery.
- Provider switching during Setup invalidates previews and configured-token selection.
- External Caddy must be provisioned with its selected module and credential independently.
- Current workspace fallback: git metadata is read-only; no commits or branch changes possible.

## Review Focus
- ENV provider differs from saved provider: saved configuration wins after restart.
- Changed provider or token cannot reuse a preview/confirmation from another account.
- DNSPod duplicate records, split lines, pagination, CNAME and exact console overrides fail safely.
- Lost DNS write responses reconcile before retry; no duplicate record creation.
- Both provider secrets remain absent from logs, JSON previews and exports.
